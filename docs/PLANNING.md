# 토스증권 연동 "관심종목 알림 + 대시보드" 통합 프로젝트 기획/설계 문서

작성일: 2026-08-12
가제: **TossWatch** (프로젝트명은 자유롭게 변경 가능)

---

## 1. 프로젝트 개요

토스증권 Open API를 활용해 두 가지 기능을 한 웹 서비스에 통합한다.

1. **대시보드**: 내 계좌·보유종목·관심종목의 시세와 손익을 한눈에 보는 웹 화면
2. **관심종목 알림**: 등록한 종목이 특정 조건(가격, 등락률, 거래량 등)을 만족하면 디스코드·이메일·대시보드 인앱 알림으로 알려주는 기능

토스 앱은 알림 조건을 세밀하게 커스터마이징하기 어렵고, 여러 조건을 한 화면에서 관리하기 불편하다는 점이 출발점이다. 이 프로젝트는 "내가 원하는 조건대로, 내가 원하는 채널로" 알림을 받고, 동시에 자산 현황을 커스텀 대시보드로 보는 것을 목표로 한다.

### 핵심 가치

- 토스증권 계좌·시세 데이터를 API로 직접 가져와 원하는 형태로 시각화
- 여러 조건을 조합한 알림 규칙을 자유롭게 설정
- 알림과 대시보드가 같은 데이터 파이프라인을 공유해 별도 관리 부담 없음

## 2. 핵심 기능 정의

### 2.1 대시보드 (웹앱)

- **자산 요약**: 총 평가금액, 당일 손익, 누적 손익률 (계좌 조회 + 보유종목 API)
- **보유종목 리스트**: 종목별 평가금액, 매입가 대비 손익, 비중
- **관심종목 리스트**: 보유하지 않았지만 지켜보는 종목의 실시간 시세, 등락률
- **차트**: 종목별 캔들 차트 (일봉 기준, 폴링 주기에 맞춰 갱신)
- **알림 히스토리**: 최근 발송된 알림 로그 (어떤 조건으로 언제 어떤 채널에 보냈는지)
- **알림 규칙 관리 화면**: 조건 생성/수정/삭제, 채널 on-off

### 2.2 관심종목 알림

알림 조건 예시 (초기 지원 범위):

- 목표가 도달 (지정가 이상/이하)
- 등락률 임계값 (예: 전일 대비 ±5% 이상)
- 거래량 급증 (평균 대비 N배 이상)
- 52주 신고가/신저가 근접

알림 채널 (사용자 선택에 따라 확정):

- **디스코드**: Webhook URL 등록 → 조건 충족 시 임베드 메시지 전송
- **이메일**: SMTP 또는 이메일 발송 API(Resend, SendGrid 등)로 발송
- **인앱 알림**: 대시보드 접속 시 알림 배지/토스트로 표시 (별도 외부 채널 없이도 확인 가능)

> 참고: 텔레그램은 이번 범위에서 제외하기로 함. 추후 확장 시 채널 인터페이스만 추가하면 되도록 설계에서 채널을 추상화한다.

## 3. 사용자 시나리오

1. 사용자가 토스증권 계정으로 Open API `client_id`/`client_secret`을 발급받아 서비스에 등록한다.
2. 서비스가 OAuth 토큰을 발급받아 계좌·보유종목 정보를 가져와 대시보드에 표시한다.
3. 사용자가 관심종목을 추가하고, 알림 조건(예: "삼성전자 7만원 이하 도달 시 디스코드로 알림")을 설정한다.
4. 백엔드 스케줄러가 주기적으로 시세를 폴링하며 조건을 체크한다.
5. 조건 충족 시 설정된 채널로 알림을 발송하고, 알림 히스토리에 기록한다.
6. 사용자는 대시보드에서 자산 현황과 알림 히스토리를 함께 확인한다.

## 4. 시스템 아키텍처

### 구성 요소

- **프론트엔드**: React 웹앱 — 대시보드 UI, 알림 규칙 설정 UI
- **백엔드 API 서버**: 프론트엔드 요청 처리, 토스증권 API 프록시, 알림 규칙 CRUD
- **스케줄러/워커**: 일정 주기로 시세를 폴링하고 알림 조건을 평가하는 스케줄 작업
- **DB**: 사용자 설정, 관심종목, 알림 규칙, 알림 히스토리, (선택) 시세 캐시 저장
- **외부 연동**: 토스증권 Open API, 디스코드 Webhook, 이메일 발송 서비스

### 데이터 흐름

```
[스케줄러] --(주기적 폴링)--> [토스증권 Open API: 시세/계좌/보유종목]
   |
   v
[조건 평가 엔진] --(조건 충족)--> [알림 디스패처] --> 디스코드 Webhook
   |                                              --> 이메일 발송
   |                                              --> 인앱 알림 DB 기록
   v
[DB: 시세 캐시, 알림 히스토리]
   |
   v
[백엔드 API] <--(조회)-- [프론트엔드 대시보드]
```

토스증권 API는 **웹소켓 실시간 스트리밍을 지원하지 않고 REST 폴링만 가능**하므로, 스케줄러가 일정 주기(예: 30초~1분)로 시세를 가져오는 구조가 필수다. 실시간성이 중요한 조건일수록 폴링 주기와 API 호출 제한(rate limit) 사이의 균형을 설계 초반에 결정해야 한다.

## 5. 토스증권 Open API 연동 설계

### 인증

- OAuth 2.0 Client Credentials Grant 방식 (서버-서버, 사용자 로그인 리다이렉트 없음)
- `POST /oauth2/token`으로 access token 발급, 유효기간 약 1시간 → 백엔드에서 만료 전 자동 갱신 로직 필요
- `client_secret`은 절대 프론트엔드에 노출하지 않고 백엔드 환경변수로만 보관

### 사용할 API 카테고리와 매핑

| 카테고리 | 기능 | 프로젝트 내 용도 |
|---|---|---|
| Auth | OAuth2 토큰 발급, JWKS | 전체 API 호출의 인증 기반 |
| Market Data | 호가, 시세, 체결, 가격제한, 캔들 | 대시보드 시세 표시, 알림 조건 평가, 차트 |
| Stock Info | 종목 마스터, 종목 경고 정보 | 종목 검색/추가, 투자유의종목 표시 |
| Market Info | 환율, 한국/미국 시장 캘린더 | 휴장일에는 폴링 스킵, 해외주식 원화 환산 |
| Account and Asset | 계좌 조회, 보유주식 현황 | 대시보드 자산 요약, 보유종목 리스트 |
| Order | (이번 프로젝트는 조회 위주, 주문 기능은 범위 밖) | 추후 자동매매 확장 시 사용 가능 |

> 이번 프로젝트는 "알림 + 대시보드"이므로 **주문(Order) API는 1차 범위에서 제외**하고, 시세 조회와 계좌 조회 중심으로 설계한다. 추후 자동매매로 확장하고 싶다면 Order API를 붙이면 된다.

## 6. 알림 시스템 설계

### 알림 규칙 데이터 모델 (개념)

- `watchlist_item`: 사용자별 관심종목 (종목코드, 등록일)
- `alert_rule`: 알림 규칙 (대상 종목, 조건 타입, 임계값, 활성 채널 목록, 활성 여부)
- `alert_log`: 발송 이력 (규칙 ID, 발송 시각, 채널, 성공/실패 여부, 메시지 내용)

### 채널 추상화

알림 발송 로직은 "조건 충족 이벤트"를 만들고, 각 채널 어댑터(디스코드/이메일/인앱)가 이 이벤트를 받아 각자 방식으로 전달하도록 인터페이스를 분리한다. 이렇게 하면 추후 텔레그램·슬랙 등 채널을 추가할 때 어댑터만 추가하면 된다.

- **디스코드 어댑터**: Webhook URL로 POST 요청, 임베드 형식으로 종목명/현재가/조건/시각 표시
- **이메일 어댑터**: SMTP 또는 이메일 API로 HTML 템플릿 발송, 다이제스트(예: 하루 한 번 모아보내기) 옵션 고려
- **인앱 어댑터**: DB에 읽음/안읽음 상태로 기록, 프론트엔드에서 폴링 또는 접속 시 조회

### 중복 알림 방지

같은 조건이 계속 충족되는 상황(예: 가격이 임계값 아래로 계속 있을 때)에 매 폴링마다 알림이 가지 않도록 "쿨다운" 또는 "조건이 최초로 충족된 시점에만 발송" 로직이 필요하다.

```

```

## 8. 화면 설계 (와이어프레임 레벨)

1. **메인 대시보드**: 상단 자산 요약 카드 → 보유종목 테이블 → 관심종목 테이블 → 최근 알림 3~5건 미리보기
2. **관심종목 관리**: 종목 검색/추가, 리스트에서 삭제, 각 종목별 "알림 규칙 추가" 버튼
3. **알림 규칙 설정**: 종목 선택 → 조건 타입 선택 → 임계값 입력 → 채널 체크박스(디스코드/이메일/인앱) → 저장
4. **알림 히스토리**: 시간순 리스트, 채널별 필터, 발송 성공/실패 표시
5. **설정**: 토스증권 API 키 등록/교체, 디스코드 Webhook URL 등록, 이메일 수신 주소 등록

## 9. 기술 스택 (확정)

> 최초 기획안은 Next.js 기반이었으나, 논의를 거쳐 아래 스택으로 확정했다.

- **프론트엔드**: React + TypeScript + Vite, 차트는 Recharts 또는 Lightweight Charts
- **백엔드**: Java 21 + Spring Boot 3.3.x (Gradle)
- **DB 접근**: Spring Data JPA (Hibernate)
- **스케줄러**: Spring `@Scheduled` 기반 (같은 애플리케이션 내 배치 작업, MVP 단계에서는 별도 인프라 없이 시작)
- **DB**: H2(파일모드)로 로컬 프로토타입 시작 → MySQL로 전환
- **레포 구조**: 모노레포 (`backend/` + `frontend/`)
- **배포**: 추후 결정

## 10. 개발 로드맵

**1단계 (MVP)**

- 토스증권 OAuth 연동, 계좌·보유종목 조회 API 연결
- 관심종목 추가/삭제
- 단일 조건(목표가 도달) 알림 + 디스코드 발송만 우선 구현
- 최소한의 대시보드 UI

**2단계**

- 알림 조건 다양화 (등락률, 거래량 급증, 52주 신고가/신저가)
- 이메일 채널, 인앱 알림 추가
- 알림 히스토리 화면, 쿨다운 로직

**3단계**

- 캔들 차트, 자산 추이 그래프 등 대시보드 고도화
- 다이제스트 알림(일일 요약 이메일)
- 필요 시 Order API 연동해 자동매매로 확장

## 11. 제약사항 및 리스크

- **웹소켓 미지원**: 실시간 스트리밍이 없어 초 단위 실시간성은 기대하기 어렵다. 폴링 주기와 API 호출 제한을 함께 고려해야 한다.
- **API 호출 제한(rate limit)**: 관심종목 수와 폴링 주기에 따라 호출 횟수가 늘어난다. 종목이 많아지면 배치 조회(가능하다면)나 캐싱을 고려한다.
- **토큰 만료 관리**: 약 1시간마다 토큰이 만료되므로 자동 갱신 로직이 필수다.
- **보안**: `client_secret`, 디스코드 Webhook URL 등 민감정보는 반드시 서버 환경변수/시크릿 매니저로 관리하고 프론트엔드에 노출하지 않는다.
- **상시 실행 환경 필요**: 스케줄러가 계속 돌아야 하므로 서버리스 함수만으로는 부족할 수 있고, 상시 실행 가능한 환경이 필요하다.
